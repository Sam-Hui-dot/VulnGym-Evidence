# 两分钟看懂 VulnGym Agent

## 它在解决什么问题

VulnGym 的一条数据会写明：漏洞从哪里进入、在哪一步造成危险、属于哪类漏洞，以及代码执行链路。
这些内容即使格式合法，也可能和真实源码不一致。T1 的目标就是自动审核这些记录。

我们的系统不会把整条记录直接交给模型猜答案。它先用 Git、源码、修复补丁和漏洞公告收集事实，再让
Judge 逐字段判断，让 Critic 主动寻找反证。没有足够证据时输出 `uncertain`，而不是强行判断。

## 一条命令看结果

在 WSL 终端中运行：

```bash
cd VulnGym-Agent
python3 scripts/show_demo.py
```

这个快速演示读取仓库中固定保存的案例摘要，不会联网，也不会消耗模型额度。它用于快速理解和录屏；
完整在线流程仍由 `prepare-evidence`、`run-semantic` 和 `build-submission` 三步组成。

## 演示案例讲了什么

WeKnora 的候选记录存在两个主要问题：

1. 它把 `NewStdioMCPClientWithOptions` 描述成真正启动子进程的位置；源码表明这一步只构造客户端，
   真正启动命令发生在后续 `Connect/Start`。
2. 它声称 Trace 已经完整连接创建请求和命令执行，却漏掉了保存配置、重新读取配置和启动进程三个
   必要阶段。

因此，系统没有因为路径和代码片段真实存在就判整条记录正确，而是把 `critical_operation` 和 `trace`
判为 `incorrect`，并给出可执行的修正链路。标题虽然与公告相似，但当前证据不能证明这种改写一定合适，
所以诚实保留为 `uncertain`。

## 你可以怎样介绍它

> 我们做的是 VulnGym T1 数据审核 Agent。它先用确定性工具收集源码、Git、补丁和公告证据，再由
> Judge 逐字段判断、Critic 主动找反证，最后输出八个字段的正确、错误或证据不足。这个案例中，
> 原记录把创建客户端误写成执行命令，还漏掉了保存、重载和启动阶段；系统不仅判错，也给出了理由和
> 修正链路。它的价值不是比 Codex 更聪明，而是让模型的安全判断可追溯、可复现，并且会主动弃权。

## 目前应当诚实说明的边界

- 这是静态证据验证，不会默认运行陌生项目或 PoC；
- TraceInspector 是轻量静态分析，不是完整跨语言污点分析器；
- 当前十条案例用于开发和未见样本验证，不能冒充官方隐藏集准确率；
- 演示摘要是已完成运行的可追溯结果，不是一次新的在线模型调用。
