## 实质审核发现

- 识别出的三条错误声明分别声称：ADK 允许带斜杠名称通过校验；FastMCP 将原始参数未经编码放入 URL；Flowise 的 getHash 用 AES 作可逆加密。源码分别显示严格名称正则、URL 编码与点号处理、bcrypt 哈希，直接反驳这些声明。
- c01、c04 的主审和复核原始标签均为支持，但 Critic 的 evidence_refs 数组为空。程序拒绝接受；评测记为输出失败，不能因为文字理由正确就记成功。
- c06 声称调用方有 DNS/私网 IP/重定向检查。主审把缺少调用方证据误当成不存在防护；Critic 指出材料不足，最终仲裁弃权。这是本轮观察到的一次真实复核分歧。
- 两组均未把 3 条错误声明接受为真。报告组大量弃权，故不能由本轮声称取证组误报率更低；当前观察支持提高可判断性。
- 取证组单看主审原始标签为 8/9 与参考一致，完整流程为 7/9：复核纠正一处过度否定，同时两次格式失败损失了可用结果。需要同时改善语义与输出可靠性。
- 模型文字仍有表述超界。例如 c01 主审把文件存在性检查归到只有部分函数体的 helper 引用；另一个已引用的主源码窗口才包含该检查。标签或有效 ID 本身不能替代逐项实质审核。

## 失败修复与独立回归

首轮完成后将 Prompt 升至 claims-judge-1.3：正式引用数组至少一项，明确禁止只在理由中提 ID；本地保留严格校验，并记录可解释的合同错误。修复不自动补猜引用，也不在失败后无限重试。两次回归均返回正式引用，c01 恢复支持；c04 虽给出支持意见和引用，却返回 looked_for_counterevidence=false，最终被保留为不足，尚未完全恢复。未强迫模型把该标志改成 true，也没有继续重跑挑结果。

c01：支持，judge_critic_completed，2 次调用；c04：不足，judge_completed，1 次调用。
回归额外 3 次调用、10,040 Token；只验证已知失败项，不并入首轮分母、不替换原来的两条失败。17 项声明合同测试与 3 项评测指标测试通过。
