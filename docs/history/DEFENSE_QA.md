# 答辩问答准备

## 1. 为什么不直接把数据扔给 Codex？

Codex 是底层推理能力，不等于这个任务的完整产品。T1 还需要确定性源码核验、公告与 commit 角色、
最小证据构造、逐字段契约、主动反证、断点恢复和效果评估。本项目不是和 Codex 比谁更聪明，而是把
同一个强模型约束成可审计、可复现、会弃权的 VulnGym 专用审核员。

## 2. 这算 Agent 吗？

算。系统会规划检查项，调用 Schema/Git/Source/Patch/Trace/Advisory/Taxonomy 工具构造证据，Judge 作出
逐字段判断，Critic 根据反证重新决策，最终由确定性适配层合并报告。模型不是一次性聊天，而是在工具、
状态、合同和反馈循环中工作。

## 3. 为什么选 T1 而不是 T2？

T1 更适合做深：输入合同明确，能同时展示静态工具、证据推理、三态决策和自评闭环。T2 生成的结果
也最终需要 T1 验证；先把验证器做扎实，后续可以自然接入 T2，而不会做出两个浅 Demo。

## 4. 为什么大量 Trace 被判错？是不是系统过严？

Blind v3 证明当时的系统确实过严：六条可辩护链路被误报，主要把未解析静态边、隐式中间步骤或
其他受影响端点的遗漏当成错误。Prompt 1.3.0 后改为评估候选链路是否在自身抽象层级可辩护；只有
节点角色、顺序、直连描述或必需 ingress/sink 被源码/Patch 反驳才判错。四条已见失败定向回归的
Trace 从 0/4 修为 4/4，但该结果只证明修复方向，不冒充新盲测。

## 5. Entry Point 和 Critical Operation 不是唯一的，怎么评？

系统判断“是否可辩护”，不要求唯一答案。多个抽象层级都合理时会保留候选和取舍；只有选中位置本身
不是输入/关键安全点，或候选描述与源码明确冲突时才判错。

## 6. 没有官方测试集，怎么证明效果？

不冒充有正式准确率。Blind v2 唯一运行 59/80，参考主要来自版本差异；随后 Blind v3 在任何预测前
完成 13 条、104 字段的公告/源码/Patch/Trace/taxonomy 证据复核，唯一运行 70/104。两组都保留原始
哈希、误报、召回、弃权和失败，不用修复后重跑覆盖。它们仍是公开数据上的自建评测，不是主办方隐藏集。

## 7. Critic 真的有用，还是重复回答？

开发回归中 Critic 曾把 21/25 提升到 25/25，也曾造成低置信回退，因此系统加入透明仲裁。Blind v3
上 Critic 只改变两个 Title，一次修正、一次引入错误，净收益为零。结论不是“Critic 一定有用”，而是
必须度量其边际收益、保存差异，并允许在没有稳定增益时关闭或约束它。

## 8. 如何控制幻觉？

确定性事实不交给模型猜；所有 correct/incorrect 必须引用当前 Packet 内存在的 evidence ID；未知引用
直接触发 contract error；证据不足时允许 uncertain；提交适配层还允许确定性源码反证否决模型结论。

## 9. 为什么不运行 PoC 或目标仓库测试？

目标仓库和依赖不可信，且不同项目构建成本巨大。本阶段默认只读 Git 与静态证据，安全且可复现。
如果官方 sandbox 明确允许动态验证，可以把它作为新工具接入，但不会让模型随意执行仓库代码。

## 10. AI Coding 留痕怎么做？

不提交私人完整聊天或隐藏推理，而是保存 Prompt 版本与哈希、实验假设、AI 完成的代码工作、人工接受
或拒绝的决策、测试结果、失败案例和 Git commit 历史。这既满足过程可复核，也避免泄露密钥和隐私。

## 11. 当前最大短板是什么？

不是代码跑不起来：当前 134 项测试、91 项必需交付文件及动态复算均已通过。最大短板是
没有独立安全专家 Gold 和官方隐藏集；TraceInspector 也仍是轻量静态分析。Blind v3 的 67.31% 说明
开放性语义泛化仍有风险，post-v3 的 31/32 只是已见失败回归，不能当成 Top 3 保证。

## 12. 批次系统性错误分析是不是“真正的根因分析 Agent”？

系统会在一批报告完成后自动聚合至少两个不同案例共同出现的证据缺口、字段错误原因、Judge 到最终
结论的变化方向和模型契约重试，并输出案例 ID、样例与改进建议。它能发现可复核的重复信号，但不会
把相关性冒充因果，所以报告明确标记为 `repeated_signal_not_proven_root_cause`。这满足“识别系统性
错误”的工程目标，同时保留人工确认根因的边界。

## 13. 如果只剩一分钟，怎么介绍亮点？

“我们做的不是另一个 Codex，而是一条 VulnGym 专用的证据审计流水线：工具证明事实，Judge 分字段
判断，Critic 主动找反证，所有确定结论必须可引用，证据不足就弃权。系统在固定开发案例中发现了
静态 import 冒充入口、反向 Trace、遗漏认证阶段和条件夸大等真实数据问题，并能用新失败驱动单变量
工程迭代；最终效果由运行前冻结的完整八字段评测单独报告。”

## 14. Blind v3 只有 67.31%，为什么还值得提交？

因为这 67.31% 是在结果不可见时一次性冻结运行得到的完整八字段结果，既统计漏检也统计误报；它比
只挑错误字段、反复调到满分更能暴露系统问题。失败被分解成 Commit 适配器全弃权、Trace 过严和
taxonomy 混淆，并推动了可复核的 Packet/Prompt/测试迭代。项目价值不只是一张分数表，还包括证据链、
三态输出、契约、恢复机制、成本优化和不覆盖失败的评估纪律。正式水平仍应以主办方最终评测为准。
