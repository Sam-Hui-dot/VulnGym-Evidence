## 数据和方法

- 固定 5 个公开开源仓库的完整 Commit，覆盖 Python、JavaScript、Go、TypeScript；仅静态读取 Git/source，未执行目标代码。
- 首次冻结 30 条语义声明：支持、矛盾、材料不足各 10 条；另有 15 条引用位置/错误片段/缺版本控制项。
- 参考判断、源码文件和 SHA-256 在调用前保存；模型仅收到声明和实际取证，未收到参考标签。
- 样本由开发 Agent 依据库源码编写并标注，尚无独立人工金标准。Werkzeug、Starlette 与早期未运行的 v2 草稿仓库有重叠，不能称作完全未见仓库盲测。
- 已知失败回归只选首次失败的 11 条，不用于估计独立准确率。另有 15 条不同函数家族的新声明，支持、矛盾、不足各 5 条；与首次数据共享仓库及 Commit，分开计分。
- 每个版本、每条样本至多一次 Judge 和一次条件 Critic，没有对单条失败重试挑选最好结果；不同修订的回归均单独保存。Judge/Critic 使用同一 Qwen3.8-Flash 模型的两个角色，不是两种独立模型。
- 确认声明的语义核验与报告候选提取分开测试；未测自然报告“自动提取→自动确认→自动判断”的整链路准确率。

### 1.7.3 新函数首轮

15 条中：4 条最终结果与参考一致，1 条实质性错误，4 条输出校验失败，6 条 Provider 调用失败。五份新报告的候选提取均因 Provider 失败而没有产出。因此，这组不足以建立稳定的新版本参考一致率，不能将 4/15 或只挑成功项的比例包装为准确率。

实质错误是 `fresh-werkzeug-03`：原声明说“调用 secure_filename 的上传业务在写入前拒绝重名，并授权目录访问”，只提供库函数证据，参考应为“证据不足”。两次模型却将其改读为“secure_filename 函数本身做这些事”，最终给出“与源码矛盾”。局部函数缺少某项操作，不能反驳未读取的业务调用方是否做了它。

这个错误说明：源码摘录可追溯、两角色意见一致，都不能保证解释遵守原声明范围。必须修复这种越界判断，并在可用账号下另跑新版本记录。

## 实际修改与仍未解决的问题

1. 模型原本需要抄写源码，出现制表符、反斜杠、引用窗口不对应等错误。当前 1.7.3 改为选择证据 ID 和行号，应用从原始源码逐字复制；不借用别的声明或不在该窗口中的代码。
2. 明确反证状态相对于“原始声明”的含义，仍保留置信度、引用归属、逐项反证和 Judge/Critic 仲裁门槛。
3. 输出仍可能将行号列表写成两个区间端点，例如 `[1032,1046]`。当前校验会拒绝这种不连续列表；本轮新样本出现 4 次，尚未消除。
4. 提取 Prompt 1.4 要求 trace 必须有至少两个明确位置，避免仅有一个位置时误分类。旧 Prompt 1.3 的五份报告产出 15 条候选：原文与字段出处均可追溯，15 条均保留了原断言范围；3 条误分为 trace 而需要用户调整。4 段代码多一个末尾换行，路径、行号和代码内容仍对应各自原文。新 Prompt 的线上效果因额度问题未验证，不能宣称分类问题已解决。

程序审计了最终保留的源码摘录与实际证据窗口是否一致；检查通过仅证明引用真实性。Agent 已核对参考理由和新样本的越界错误，仍未进行独立人工参考复审、真实用户报告评估或完整漏洞/补丁/污点分析准确性验证。
