## 产品定位

一句话：开发者收到一份漏洞报告后，工具对照指定版本的代码，逐条检查报告描述是否得到源码支持，并给出可以打开的证据。

首先面向开源维护者和参与开源开发的学生开发者。任务从“收到报告”开始，到“导出可以继续审阅的报告”结束。

首页文案：

> 收到漏洞报告，先核对它的代码依据。
>
> 选择项目与版本，粘贴报告。AI 整理需要核查的内容，你确认后，工具读取源码，逐条说明哪里一致、哪里矛盾、哪里还缺材料。

主按钮：“开始核对报告”。辅助按钮：“加载演示报告”。

保留报名名称“VulnGym Evidence：漏洞报告证据复核智能体”。名称不改，解释与流程重新组织。

## 三个页面

### 1. 导入报告

首屏只展示项目选择、版本、报告和主操作。CVE、公告、手动声明和 JSON 编辑折叠到高级选项。

选择项目时显示代码准备状态和版本是否可读。当前程序读取本地仓库；任意 GitHub 地址自动拉取尚未实现。新版先把本地仓库的导入/映射讲清，不能用界面暗示已经支持所有远程仓库。

演示入口预填公开仓库和准确版本，并明确标注“基于真实源码编写的演示报告”。正常使用不能猜测被审查版本；缺版本时提示补充。

### 2. 确认内容

左侧报告原文，右侧待核对句子。选择候选时高亮对应原句。

每张候选卡显示原句、核查目的、文件/行号，以及缺失字段。AI 没有提取到的字段不能编造。用户可以编辑、移除，再确认本次范围；候选不会自动发起复核。

代码、行号等修改工具保留，但不把旧版长表单铺满主页面。确认后按实际阶段事件显示进度。

### 3. 复核结果

顶部显示任务、固定版本和本次执行状态；逐条列出结果，不生成“整个仓库安全”的总评分。

左侧为报告句子列表，右侧为当前选中项的中文解释及源码。报告原句、解释、文件路径、相关源码同时可见，点击可定位关键行。

正文范例：

> 与源码矛盾
>
> 报告说这里没有进行编码。实际代码在替换参数之前已执行编码和点号处理，报告遗漏了前一步。

源码摘录保持原文；中文解释须来自实际复核，不用固定模板替换模型判断。原始输出和完整取证记录放在展开区。

固定四类界面状态：

| 状态 | 意义 | 下一步 |
| --- | --- | --- |
| 引用/描述得到支持 | 本条指定范围内找到支持依据 | 阅读代码并继续审阅 |
| 与源码矛盾 | 找到反驳这句话的代码 | 检查依据，修订报告 |
| 证据不足 | 已读材料不能确定这句话 | 显示缺少的材料，人工补充 |
| 复核未完成 | 模型调用或输出不符合要求 | 显示具体原因；保留记录后处理 |

证据不足与执行失败必须分开显示。结果导出集中在顶部/底部固定位置，支持当前已有 JSON、Markdown 和完整 HTML。

## 视觉规则

浅灰底、白色工作区、深色正文、单一蓝色主操作。状态同时用文字、图标和颜色表达。正文约 16px，关键解释约 18px，代码为等宽字体。减少细碎提示与重复边框。

桌面结果页以“左侧句子列表 + 右侧解释与代码”为主，避免旧版左侧长表单、右侧空白。窄屏依次展示内容，不压缩成三列小字。

页面设计示意见 UI_PROPOSAL.html。其中显示的三项结果是设计内容，合并案例尚未运行；图中按钮用于切换设计页面，不连接模型和现有服务。

## 实施顺序及审核点

1. 本稿、三页布局和口播稿先审核，确认用途与主案例。
2. 在 v2 实施三步交互，处理仓库准备提示、状态区分、中文解释和过长摘录。
3. 准备同一报告的三条声明，跑通一次新的完整提取、确认、取证、判断与导出。
4. 根据实际页面和实际结果校准脚本，给出可直接照做的最终录制入口与操作表。
5. 参与者录制后，再回看画面、核对文案和提交材料。
