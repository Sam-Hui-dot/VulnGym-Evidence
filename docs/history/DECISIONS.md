# 架构与评测决策记录

本文记录会影响系统行为、评测结果或可复现性的关键决策。实现细节变化可以进入 Git 历史，
但下列原则发生变化时必须同步更新本文。

## D-001：主线选择 T1 数据自动化验证系统

- 日期：2026-08-19，2026-08-25 复核。
- 状态：采用。
- 决策：优先完成已有 VulnGym 记录的字段级验证，不同时铺开完整 T2 漏洞抽取系统。
- 理由：T1 的输入边界更清晰，可从公开已验证记录构造开发集和留出集，适合建立可量化优化闭环；
  T2 所需的公告理解、漏洞版本定位、全仓发现和完整链路生成可以复用本项目工具，但不应分散主线。

## D-002：证据优先，允许诚实弃权

- 日期：2026-08-19。
- 状态：采用。
- 决策：每个字段输出 `correct / incorrect / uncertain`、置信度、理由和证据。
- 理由：Schema、Git 和源码事实不应交给模型猜测；证据缺失、来源冲突或调用边不可证明时，
  `uncertain` 比高置信度幻觉更符合题目要求。

## D-003：不执行被审计仓库中的陌生代码

- 日期：2026-08-19。
- 状态：采用。
- 决策：默认只使用 `git cat-file`、`git show`、源码读取、搜索和静态分析。
- 理由：上游仓库不可信且依赖复杂；题目允许在出题方 sandbox 中执行，但本地预研阶段没有必要扩大风险面。

## D-004：内部严格契约与外部格式解耦

- 日期：2026-08-25。
- 状态：采用。
- 决策：内部保留包含 evidence reference、自检和 correction 的严格 Judge/Critic 结构；
  面向正式评测增加薄适配层，输出主办方最终指定的 JSONL Schema。
- 理由：新版 PDF 给出了示例输出，但多处明确标注验收阈值或难度仅作参考。解耦可以避免
  正式接口变化迫使核心推理逻辑重写。

## D-005：Judge→Critic 负责语义反证，确定性工具负责事实

- 日期：2026-08-20。
- 状态：采用。
- 决策：Judge 先逐字段判断，Critic 主动寻找反证；commit、路径、行号、代码和 Schema 等事实
  由确定性工具校验。
- 理由：Pilot 中 4/5 案例在 Critic 后至少一个字段发生变化，说明一次性模型输出不够稳定；
  同时，事实性检查不需要消耗模型的不确定推理能力。

## D-006：只允许显式、可审计的派生字段修复

- 日期：2026-08-20。
- 状态：采用。
- 决策：当五个字段结果均合法、但 overall verdict 与字段结果矛盾时，可以离线重算 overall；
  必须保留模型原始输出、修复动作和修复前后验证结果。
- 理由：这属于确定性派生值纠错，不应再次调用模型；任何字段语义变化仍须由 Judge/Critic 产生。

## D-007：AI 使用透明但不泄露秘密

- 日期：2026-08-25。
- 状态：采用。
- 决策：记录 AI Coding 的任务、主要改动、验证和人工决策，不提交 API Key、访问令牌、
  私人完整对话或模型隐藏推理过程。
- 理由：题目允许任意 LLM 并建议保留 AI Coding 使用记录；高层审计日志比原始聊天转储更可复核。

## D-008：会议口径优先于 PDF 示例

- 日期：2026-08-25。
- 状态：采用。
- 决策：PDF 中的输出结构、字段权重、难度分层、分数阈值和 Agent 形式均作为设计参考，
  不作为唯一验收合同。最终报告优先服务使用者理解，并展示证据、冲突、候选修正和不确定原因。
- 理由：项目负责人在宣讲会上明确说明这是开放性问题，重点考察问题理解、Agent 设计、
  工程化能力、过程记录和自建评估机制，而非固定测试集排行榜。

## D-009：不使用固定行号容忍窗口

- 日期：2026-08-25。
- 状态：采用。
- 决策：取消“声明行附近 ±5 行找到相同代码即自动 correct”的规则。源码工具区分 exact、
  drifted、ambiguous 和 missing；唯一漂移位置可作为修正候选，但原 `{file, line, code}` 仍被报告为不一致。
- 理由：项目负责人明确否定固定 ±5 行规则。固定窗口既可能接受错误位置，也可能拒绝合理重定位，
  无法表达多匹配和语义等价情况。

## D-010：Critical Operation 是可论证的安全关键点，不保证唯一

- 日期：2026-08-25。
- 状态：采用。
- 决策：Critical Operation 可以是危险 sink、鉴权决策、状态改变、缺失检查或绕过点；
  不假设它必须是“应该 return 但没有 return”的判断。证据支持多个候选时，报告候选及取舍。
- 理由：复杂逻辑漏洞和多阶段漏洞可能存在多个合理锚点，评估重点是分析逻辑而不是匹配唯一答案。

## D-011：Prompt 是可版本化的运行资产

- 日期：2026-08-25。
- 状态：采用。
- 决策：Judge 和 Critic Prompt 使用稳定 ID、语义版本和规范内容 SHA-256；每条运行结果保存实际
  Prompt 元数据。Prompt 变更必须记录假设和验证，不用覆盖旧结果的方式制造不可追溯对比。
- 理由：宣讲会明确要求展示 Prompt 设计、调试过程和 AI Coding 历史。仅在源码里直接改字符串无法
  证明某次结果对应哪版 Prompt，也不利于失败案例驱动的迭代。

## D-012：语义评测必须使用独立人工 Gold

- 日期：2026-08-25。
- 状态：采用。
- 决策：语义准确率只针对独立人工复核的五字段 gold 计算；Agent 自己的输出、公开记录的
  `verify=1` 或 Judge/Critic 一致性都不能直接当作语义真值。没有 gold 的 Pilot 只报告运行状态、
  输出分布、成本和 Judge→Critic 变化。
- 理由：Entry Point、Critical Operation 和业务逻辑 Trace 可能多解，历史数据也可能只是标注口径变化。
  让 Agent 生成并评价自己的答案会造成循环论证，无法证明系统效果。

## D-013：公告证据离线优先且 commit 角色必须显式

- 日期：2026-08-25。
- 状态：采用。
- 决策：审计阶段只读取显式提供的本地公告缓存；公告必须以 CVE/GHSA 或规范来源 URL 匹配，
  不按仓库名猜测。普通 `/commit/<sha>` URL 仅记为 referenced commit，只有缓存明确标注
  `vulnerable_commits` / `fixed_commits` 时才用于相应角色的确定性结论。
- 理由：同一仓库可有大量漏洞，而公告引用通常指向修复 commit。弱匹配或混淆 commit 角色会产生
  比缺失证据更危险的高置信错误。

## D-014：Trace 连续性使用分层静态证据

- 日期：2026-08-26。
- 状态：采用。
- 决策：TraceInspector 不执行目标项目代码。第一层识别同函数顺序、反向顺序和跨函数直接符号调用；
  只有未证明或反向边才附加扩大后的函数/代码块上下文。`same_file_order` 只表示位置顺序，不冒充调用或数据流证明。
- 理由：固定窗口经常缺失真实调用边，而把所有函数体都交给模型会显著增加 Token 和噪声。分层策略保留
  可审计的结构信号，并把模型资源集中到真正缺证据的边。

## D-015：非确定 Provider 的单次 A/B 不等同于因果证据

- 日期：2026-08-26。
- 状态：采用。
- 决策：Provider 无固定 seed 时，单次 paired run 只用于发现趋势和失败案例；出现非目标字段变化时，
  不将差异归因于被测工具。正式效果结论至少需要人工 gold，并优先采用可固定参数的 API 或多次重复运行。
- 理由：TraceInspector A/B 中两个未针对的 Entry 字段也发生变化，证明模型采样波动足以混淆单次对比。

## D-016：公告缓存保存可引用事实，不只保存标题和链接

- 日期：2026-08-26。
- 状态：采用。
- 决策：公告缓存可以保存经来源核对、长度受限的 `facts`、CWE 和影响/修复版本，并将其作为公告文档
  的一部分交给 Judge；事实必须是来源内容的忠实转述并保留官方 URL，不保存无法追溯的模型推断。
- 理由：只有标题、编号和 commit 角色不足以裁决传播路径和执行位置。WeKnora 公告明确给出了
  `storage -> reload -> Connect -> Start`，缺少这些事实会让 Agent 对错误 sink 被迫弃权。

## D-017：Trace 的“证据缺失”和“已证明缺环节”使用不同判定

- 日期：2026-08-26。
- 状态：采用。
- 决策：Packet 没覆盖某条边时优先 `uncertain`；公告、补丁或源码已经指出漏洞所需阶段，而候选 Trace
  漏掉该阶段或作出相反描述时判 `incorrect`。单纯 exact source match 不证明完整 Trace。
- 理由：二者分别对应审计系统证据不足和候选数据本身不完整，混为一谈会造成系统性过度弃权。

## D-018：四条争议样本复核后冻结当前 Prompt 与 Packet 合同

- 日期：2026-08-26。
- 状态：采用。
- 决策：Packet 0.4.0 与 Prompt 1.1.0 在 n8n、WeKnora、OpenClaw、Google ADK 完成证据复核后冻结；
  不再为消除 n8n Entry 的单一粒度分歧修改规则。下一轮改进必须由新增样本或新的失败类型驱动。
- 理由：当前与 provisional 参考集仅剩多锚点口径差异，继续围绕同四条调参会提高过拟合风险，不能证明
  对隐藏数据的泛化能力。

## D-019：分类判断必须引用 VulnGym 自身 taxonomy

- 日期：2026-08-26。
- 状态：采用。
- 决策：Evidence Packet 0.5.0 为匹配到的业务逻辑 L1/L2 标签提供版本化 taxonomy 证据；模型仍需结合
  公告与源码判断漏洞语义是否符合标签，不能因“标签存在”直接判正确。Prompt 1.1.0 保持不变。
- 理由：未见样本 entry-00146 的 `业务逻辑 / BL-AGENT-CAPABILITY` 是 VulnGym 正式标签，但 Packet 0.4.0
  未提供定义，导致 Agent 对两个正确字段弃权。补充 taxonomy 后，单变量复跑只修复这两个字段。

## D-020：基线必须固定同一底层模型

- 日期：2026-08-28。
- 状态：采用。
- 决策：比较“直接扔给模型”和专用 Agent 时，使用同一个 Provider、模型和输出合同；裸基线只移除
  外部证据与工具，不更换为更弱模型。
- 理由：这样才能把差异主要归因于 Agent harness，而不是模型能力差异，避免稻草人基线。

## D-021：仓库级留出变异只评估预登记目标字段

- 日期：2026-08-28。
- 状态：采用。
- 决策：每个案例来自不同仓库，donor 不得与目标仓库相同；模型运行前固定变异字段、原值、新值、
  donor 和内容哈希。只计算目标字段检出，不把未变异字段自动视为人工 Gold。
- 理由：既避免跨 split 内容泄漏，也避免在开放性字段上用生成器自己的记录循环证明正确性。

## D-022：完整证据落盘，模型只接收紧凑可引用视图

- 日期：2026-08-28。
- 状态：采用。
- 决策：删除模型请求中的重复 Trace 源码窗口、本地路径和未选中 patch 候选的无界文件列表；完整
  Evidence Packet 不删减，仍用于审计和重放。
- 理由：10 条实验中请求字符下降 55.6%、Token 下降 50.9%，目标字段检出保持 12/12。运行审计能力
  与模型上下文效率不应被绑定为同一个数据结构。

## D-023：Critic 通过置信度门仲裁，不无条件覆盖 Judge

- 日期：2026-08-28。
- 状态：采用。
- 决策：Judge/Critic verdict 不同时，Critic 只有在置信度相等或更高时才能覆盖；低置信分歧保留为
  `arbitration` 元数据并选择 Judge。最终 overall 从选中字段确定性重算。
- 理由：仓库级开发实验中 Critic 把正确检出的反向 Trace 从 `incorrect, 0.70` 回退为
  `uncertain, 0.55`；旧实验也存在 `uncertain, 0.60 -> incorrect, 0.80` 的有效改进。该规则同时保留
  高置信修正与阻止低置信静默退化。置信度尚未校准，因此该门必须作为可审计工程策略而非概率真理。

## D-024：被用于修正规则的数据降级为开发评测

- 日期：2026-08-29。
- 状态：采用。
- 决策：`repo-holdout-v1` 保留原 benchmark ID 和结果，但统一更名为仓库级开发评测。因为该组
  Critic 回退直接推动 non-regression gate，修正后的 12/12 不再作为独立盲测成绩。
- 理由：只要看过某组失败并据此改变系统行为，同组后续结果就含有开发反馈。继续称其为最终 holdout
  会高估泛化证据，即使代码与实验结果本身都真实。

## D-025：冻结盲测必须同时衡量检出和误报

- 日期：2026-08-29。
- 状态：采用。
- 决策：`blind-v2` 在模型运行前冻结行为 commit、Prompt/Packet 版本、案例、来源和哈希；使用 8 个
  未参与开发的仓库、5 条真实历史修订和 5 条 `verify=1` 干净记录。评测覆盖八字段完整报告，至少输出
  accuracy、incorrect precision/recall/F1、abstention、case exact match 和 confusion matrix。
- 理由：只给有意错误字段计分可以测试召回，却无法发现系统是否把大量干净字段误判为错误。完整标签
  与干净样本让“抓得住错误”和“不会乱报错”同时进入证据链。

## D-026：不可比较的 Patch 宁缺毋滥

- 日期：2026-08-30。
- 状态：采用。
- 决策：只有官方修复 commit、公告直接引用的 PR head，或官方 patched-release commit 与候选版本形成
  可解释局部差异时才加入 fix map。供应链标签恢复、无官方修复、或跨维护分支产生巨型无关 diff 的案例
  不提供 Patch，明确让 Agent 依赖公告、固定源码和 Trace 证据，证据仍不足则输出 `uncertain`。
- 理由：Patch 数量不是质量指标。把几百个无关文件的跨分支差异包装成修复证据，会放大 Token、干扰
  判断，并让评审无法复核，风险高于诚实声明缺失。

## D-027：多行 `code` 的整数 `line` 表示起始行

- 日期：2026-08-30。
- 状态：采用。
- 决策：当 `line` 为单个整数且 `code` 为多行时，从该整数开始读取与代码行数相同的源码范围；显式
  行号区间仍按区间处理。仅因代码覆盖 `line..line+n` 不再判为位置漂移。
- 理由：Blind v2 的 Airflow `139` + 三行代码被旧实现读成单行并高置信否决，属于工具语义错误而非
  安全判断分歧。

## D-028：省略号摘要不参与确定性逐字否决

- 日期：2026-08-30。
- 状态：采用。
- 决策：`code` 中存在独立 `...` 占位行时，源码工具输出 `uncertain` 的 summary-placeholder 证据，
  交给语义层结合上下文判断；不把占位符当真实源码逐字搜索，也不自动判 correct。
- 理由：摘要既不能证明完整源码一致，也不能证明候选错误。旧实现对 FastMCP 摘要产生多个 0.98
  置信误报，违反“确定性事实才可否决模型”的边界。

## D-029：标题是第六个语义字段

- 日期：2026-08-30。
- 状态：采用。
- 决策：公告标题逐字相等可直接确认；措辞不同则由 Judge/Critic 比较产品、弱点、影响与组件，不能由
  适配层固定弃权。Prompt 升至 1.2.0。公告明确给出编号而候选 `vuln_ids` 为空时仍按缺失错误处理。
- 理由：标题正确性是语义等价问题。Blind v2 的 10/10 固定弃权证明字符串相等策略不具备可用性。

## D-030：多行起始锚点命中但正文不一致时交给语义层

- 日期：2026-08-30。
- 状态：采用。
- 决策：多行候选在声明起始行命中首行锚点、但完整文本因摘要、docstring 或等价表现不一致时，确定性
  层输出 `uncertain`；单行不匹配、文件缺失、或完整代码明确只出现在其他位置仍输出 `incorrect`。
- 理由：确定性否决必须建立在可证明的矛盾上。仅凭多行展示文本不逐字一致无法区分错误代码和摘要表达，
  而 Packet 已提供带行号真实源码，语义层可以继续审核其角色与含义。

## D-031：失败驱动后的 Evidence Packet 升级到 0.6.0

- 日期：2026-08-30。
- 状态：采用。
- 决策：多行起始行、summary-placeholder 和 anchored-summary 三项证据语义落地后，将 Packet 从 0.5.0
  升到 0.6.0；Blind v2 原始运行继续绑定 0.5.0，后续 Blind v3 绑定 0.6.0。
- 理由：即使 JSON 顶层结构兼容，确定性证据的 verdict 与 field 命名已经改变。显式版本升级能避免把
  修复前后结果当作同一 Agent 行为。

## D-032：版本差异只生成候选标签，不能直接充当 Gold

- 日期：2026-08-30。
- 状态：采用。
- 决策：Blind v3 的每条案例必须在 selection 中提供完整八字段 review；`selection_status=frozen` 时，
  构建器拒绝任何未复核案例。参考标签允许 `correct / incorrect / uncertain`，并同时保留 provisional
  版本差异标签、复核者和理由。
- 理由：Blind v2 证明后续版本修改可能只是描述、行号范围或另一种同样合理的选点。反过来，`verify=1`
  的记录也可能存在空编号或 taxonomy 与公告语义冲突。只有公开证据交叉复核后才适合作为评测参考。

## D-033：Blind v3 采用 entry/report 隔离，不伪称仓库隔离

- 日期：2026-08-30。

## D-034：Commit 需要可审计修复关系，存在对象本身不够

- 日期：2026-08-30。
- 状态：采用。
- 决策：公告显式 vulnerable commit 仍是最强证据；否则只有当 PatchInspector 选中修复、候选正是

## D-035：Trace 评估可辩护链路，不要求穷举实现生命周期

- 日期：2026-08-30。
- 状态：采用。
- 决策：Trace 必须包含其自身主张所需的攻击者影响和安全关键操作，但不强求全部受影响端点、隐式
  helper、框架存储/重载或每个生命周期步骤。`unresolved/same_file_order` 仅表示静态工具未证明边，

  其他端点。负责人已明确链路可能多解，轻量 TraceInspector 也不是完整污点分析器。

## D-037：完整字段语义优先于“位置大致合理”

- 日期：2026-09-03。
- 状态：采用。
- 决策：Entry/Critical 按 `file + line + code + desc` 的完整提交值审核，Trace 按节点、描述、角色、
  顺序和转移的完整提交值审核。候选位置可以是可辩护的安全相关点，但描述若把构造/准备阶段误写为
  实际副作用激活点，该字段仍判 `incorrect`。允许省略中间实现阶段的前提是省略后显式描述依然为真。
- 理由：导师明确允许多解和不同抽象粒度，这不等于忽略候选自己的事实主张。WeKnora 开发案例中，
  `NewStdioMCPClientWithOptions` 是可辩护的数据交接点，但候选声称它直接启动进程；源码和公告把启动
  放在后续 `Connect -> Start`。Prompt 1.5.0 用通用生命周期规则区分这两件事，不硬编码案例答案。

## D-042：Commit 正确性必须建立在非循环 provenance 上

- 日期：2026-09-08。
- 状态：采用。
- 决策：废除“唯一直接子提交 + 0.75 置信度即可验证 Commit”的门槛。只有可信 fix-map 或公告显式
  fixed/supporting-fix 角色、候选到修复的 Git 祖先关系、可检查源码差异三者同时成立时，Commit 才能
  确定性输出 `correct`。其余证据分为 `supported` 或 `weak` 并安全弃权。
- 理由：Git 拓扑只能证明先后关系，不能证明后一个提交修复了前一个提交中的漏洞。README、锁文件或
  普通功能提交均可成为唯一子提交；用它反推漏洞身份属于循环论证。Post-v6 零模型重放将三项旧
  `correct` 降为 `uncertain`，并保留冻结 Blind v6 原成绩作为历史事实。

## D-043：跨文件证据只做可审计的一跳解析
