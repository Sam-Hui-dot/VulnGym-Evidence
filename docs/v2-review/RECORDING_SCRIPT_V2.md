# VulnGym Evidence v2：拍摄脚本与逐镜头口播

2026-10-04。审核稿。目标约 3 分钟，最终长度服从报名页面要求。

本稿参考原 VulnGym-Agent 的 docs/DEMO_SCRIPT.md、docs/RECORDING_GUIDE.md 和 scripts/run_recording_demo.sh：项目介绍 → 方案 → 展示输入 → 真实运行 → 本次报告 → 价值与边界。原来约 4 分钟的工程答辩结构，调整为围绕一个使用任务的产品演示。

录制由项目作者完成。协作者负责脚本、文案、演示数据、操作步骤和准备；本轮不生成自动配音视频。

## 这条视频必须回答什么

1. 谁用：开源维护者和参与开源开发的学生开发者。
2. 为什么用：报告写得完整，仍可能误解代码，查证需要回到指定版本。
3. AI 做什么：提取核查内容，结合工具取得的源码解释语义，必要时追加反证复核。
4. 得到什么：逐条结论、可以打开的依据和可导出的审阅报告。

## 主案例

- 项目：公开仓库 PrefectHQ/fastmcp。
- 固定版本：40bdfb6b1de0ce30609ee9ba5bb95ecd04a9fb71。
- 文件：src/fastmcp/utilities/openapi/director.py。
- A：第 215 行引用与代码一致，用于说明“引用存在”与“描述成立”分开核对。
- B：报告声称没有 URL 编码和点号处理；主画面展示对第 214 行的查证。
- C：报告声称所有请求的调用方均检查 DNS、私网地址和重定向；展示超出已读材料时需要补充依据。

这是基于真实源码构造的教学演示报告，不是维护者实际收到的举报，也不表示发现了一个新漏洞。画面保留简短来源标记。

v1 单条检查已有 B 的矛盾结果及 C 的不足结果。v2 合并报告及新交互尚未运行，下面的结果段落以新一次实际执行为准。若输出不同，先保存并排查，不照念预期结果。

## 0:00-0:20：问题与使用者

画面：项目首页。报告卡片中可见“没有对参数编码”这句话，暂不展示结论。

口播：

> 开源项目收到漏洞报告后，开发者还要回到代码里查证：报告描述的行为，真的发生在这个版本里吗？报告可能引用了真实代码，却遗漏了前后的处理。VulnGym Evidence 就用来完成这一步复核。

操作：鼠标停在报告原句附近，不滚动代码，不先展示全部结果。

## 0:20-0:40：项目介绍与输出

画面：产品定位及导入入口。展示“报告 → 用户确认 → 源码复核 → 审阅报告”的四步说明。

口播：

> 它面向开源维护者和开发者。用户提交报告、代码项目和指定版本，AI 整理待核查的句子，工具读取源码，再给出逐条结论和依据。最后得到一份可以继续讨论、修订和复查的审阅报告。

操作：进入“导入报告”。前两段集中介绍项目，不堆砌 Judge、Packet、合同等内部名称。

## 0:40-0:55：AI 与工具如何配合

画面：简短四步说明，或停留在准备好的输入。

口播：

> 程序负责固定版本、读取代码和核对引用，AI 负责结合上下文解释报告。必要时，系统会追加反证复核，并检查引用是否确实来自所读取的源码。

技术问答可补充：主审与复核是同一配置模型的两个角色，不是两个独立模型；源码摘录可追溯不保证所有解释都正确。主视频不展开全部提示词。

## 0:55-1:35：展示输入并现场运行

画面：同一份报告的输入、候选和确认按钮，再进入实际执行进度。

口播：

> 这里使用一份基于公开代码编写的演示报告。它有三条待核对内容，其中一条声称路径参数没有经过编码。我点击提取，先检查 AI 是否正确理解原句，再确认这三条内容，开始复核。

操作：

1. 选择已准备好的 fastmcp 项目和准确版本。
2. 粘贴完整 DEMO_REPORT.txt；不要导入参考结论。
3. 点击提取，让本次实际调用生成候选。
4. 对照原文确认候选；需要补充时，只填报告已有内容，不凭空补充。
5. 点击确认，触发取证及模型复核。显示真实阶段、任务 ID 和本次执行标记。

等待中的可选口播：

> 现在读取的是指定历史版本的代码，后面出现的结果会来自这一次执行。

实际耗时超过预计时，先保留完整原始录屏；剪掉纯等待时显示“等待过程已剪短”。不能把旧任务报告换进来，不使用伪造进度。

## 1:35-2:15：重点演示报告写错在哪里

画面：本次结果。优先选中 B，左侧显示报告原句，右侧显示中文解释及第 214-215 行代码。

预期得到矛盾结果时的口播：

> 重点看这一项。报告说没有进行编码，但实际代码在替换参数之前，已经完成编码和点号处理。工具把报告原句、解释和源码放在一起，我能直接看到它为什么指出矛盾。这一处引用确实存在，却不能支持报告给它的解释。

操作：先读一句中文结论，再指向关键代码。可短暂选择 A，说明引用位置一致；马上回到 B，避免把主视频变成行号检查。

如果结果为执行失败或不足：本段不能照读。记录原因，暂停录制，修复或重新选择经查证可展示的范围。后续重跑记录完整保留，不能把演示挑选结果写成盲测成绩。

## 2:15-2:35：缺证据时怎么处理

画面：选择 C，显示缺少调用方和实际请求执行材料。

预期得到证据不足时的口播：

> 另一项声称所有请求都经过网络防护检查。但当前读到的代码只展示请求对象的构造，没有实际发送时的调用方。这里保留证据不足，并说明还缺什么材料，方便开发者继续查证。

操作：指向缺失材料提示。不要将“未读到防护”讲成“防护不存在”。模型输出格式失败属于复核未完成，不使用本段台词解释失败。

## 拍摄准备与停机条件

- 页面确认并实现后，协作者补齐最终按钮名称、打开顺序和确切命令；本稿不是现在即可照点的操作说明。
- 先实际预演同一报告，确认原文、候选、三项结果、源码定位及导出对应同一次任务。
- 正式录制使用独立的新任务，保存原始录屏和任务结果。提取、语义复核的实际调用分开记录。
- 录制前配置模型与本地代码，不录制密钥输入过程。页面中文字、代码和旁白优先于背景音乐与转场。
- 发生网络错误、模型错误或结果无法解释时，停止本次拍摄并保留记录；先查问题，不连续点击重跑。
- 独立打开旧结果时明确标记“已保存结果”；这只作为备用说明，不能替换主流程中的新结果。
- 本次视频不加入 T1 的旧指标。当前作者标注的小样本对照留在技术附件，不包装成泛化准确率。

建议录制 1080p、30fps，正文和代码调到能直接阅读的字号。可一次完整录制后只剪纯等待与首尾；也可分段录口播，但核心输入到结果保留同一次真实执行。
